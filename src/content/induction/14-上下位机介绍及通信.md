本文讲的是一套**通用的理解框架**，不依赖任何具体车、板卡、仓库或通信协议。读完后，你应能面对一份新的自瞄项目时，快速找到上位机与下位机的职责边界，知道应该从哪里阅读、可以修改哪里，以及哪些部分应交给电控负责人。

## 1. 为什么自瞄要分上下位机

自瞄系统同时要做两类性质不同的工作：

- 看图、识别装甲板、预测运动，需要较强的算力和 Linux 环境；
- 读取电机反馈、毫秒级闭环控制、驱动 CAN 电机，需要稳定且实时的嵌入式系统。

因此通常将系统分为上下位机：

```mermaid
flowchart LR
    camera[相机图像] --> upper[上位机：检测、解算、跟踪预测、生成云台目标]
    upper -->|串口 / USB / CAN 等通信| lower[下位机：限幅、滤波、PID]
    lower --> motor[云台电机]
    motor -->|角度 / 速度反馈| lower
    lower -->|当前姿态与设备状态| upper
```

上位机给下位机的通常是“云台应看向哪里”，目标角速度或工作模式；下位机根据编码器、IMU 等反馈决定“怎样稳定地到达那里”。上位机不直接输出电机电流，下位机也不需要理解图像里是否出现了装甲板。

| 角色 | 主要工作 | 典型输入 | 典型输出 |
| --- | --- | --- | --- |
| 上位机 | 相机采集、识别、位姿解算、跟踪、预测、目标选择 | 图像、相机参数、下位机反馈 | 目标角度、目标速度、工作模式 |
| 下位机 | 传感器读取、通信接收、滤波、PID、安全状态与电机控制 | 上位机目标、编码器/IMU/遥控器状态 | 电机命令、当前姿态、设备/比赛反馈 |

调试也应遵守这个方向：先确认目标识别与目标值是否合理，再确认通信数据的单位、符号和时效，最后才观察云台动作。方向相反、单位混用和旧数据未超时，都会表现得像“PID 没调好”。

## 2. 两种常见上位机：NUC 与 NVIDIA Jetson NX

两者都可以运行 Linux 和 ROS 2，也都能承担相机、检测、跟踪和通信任务；区别主要在硬件架构与深度学习推理后端。

| 平台 | 特点 | 常用推理路径 | 关注点 |
| --- | --- | --- | --- |
| Intel NUC | x86 平台，Intel CPU/iGPU | OpenVINO 或 CPU 推理，通常使用 ONNX 模型 | x86 依赖、CPU/iGPU 占用、散热 |
| NVIDIA Jetson NX | ARM 平台，NVIDIA GPU | CUDA/TensorRT 推理 | JetPack、CUDA/TensorRT、显存与散热 |

对控制链路而言，两台机器输出的 ROS 消息和发给下位机的控制命令应该一致；切换 NUC/NX 不应改变坐标系、角度单位或通信协议。

TensorRT 的 Engine 通常与 GPU 架构、CUDA 和 TensorRT 版本相关，应在最终运行的 Jetson 上生成；不要直接复用另一台机器生成的 Engine。这个差异发生在“图像如何推理”的层面，不发生在“下位机怎样驱动电机”的层面。

## 3. 如何理解上位机工程

上位机常以 ROS 2 workspace 组织。一个健康的工程会把模块按职责拆开，让你可以从数据流而不是从几千行代码开始阅读：

```mermaid
flowchart LR
    sensor[相机 / 外部传感器] --> adapter[camera / sensor adapter]
    adapter --> detector[detector]
    detector --> tracker[tracker]
    tracker --> controller[controller]
    controller --> driver[serial driver]
    driver --> lower[下位机]
```

常见 ROS 2 包及职责如下：

| 包类型 | 责任 | 阅读时重点看什么 |
| --- | --- | --- |
| `camera` | 发布图像与相机内参 | 图像话题、分辨率、时间戳、相机坐标系 |
| `detector` | 从图像找出候选目标 | 输入输出消息、置信度、模型/传统视觉参数 |
| `tracker` | 关联目标、平滑状态、处理短时丢失 | 目标有效条件、超时、预测结果 |
| `controller` | 将目标位置转成云台目标 | 坐标变换、单位、限幅、上层控制策略 |
| `serial_driver` | 将 ROS 消息编解码为实际通信帧 | 字段顺序、长度、校验、重连与超时 |
| `robot_description` | 维护传感器、云台与相机的坐标关系 | TF 树、外参、命名约定 |
| `launcher` | 组合节点并加载不同运行参数 | 启动顺序、比赛/调试 profile、参数文件 |
| `recorder` | 录制传感器、目标、命令与反馈 | 是否能复现一次调参或故障 |

其中最值得先读的是 **消息定义、参数文件和启动文件**。它们告诉你模块之间交换的是什么数据、以什么单位运行、当前启用了哪套参数；读懂这些后再深入某个算法实现，效率最高。

## 4. 下位机：一个 CubeMX 项目的通用框架

下位机通常是一个 STM32 固件工程。它最终会被交叉编译成 `.elf`、`.hex` 或 `.bin`，烧录到 MCU 的 Flash 中运行；它不是另一个 ROS 工程。

CubeMX 的角色是把硬件配置变成初始化代码：选择 MCU、配置时钟、引脚、CAN、UART、DMA、定时器和中断，再生成基础工程。团队代码则在这个基础上实现通信、控制和机器人行为。

```mermaid
flowchart TD
    ioc[.ioc：CubeMX 配置] --> core[Core / Drivers / 启动文件]
    core -->|HAL API / 中断回调| components[components / middleware<br/>通信、PID、滤波、电机等可复用模块]
    components -->|绑定实际设备| instance[instance / device<br/>电机、传感器、串口协议实例]
    instance -->|调度与机器人逻辑| app[task + robot / application<br/>控制周期、状态机、目标与安全保护]
```

目录名称会因团队而异，但职责通常能对应到下面的表：

| 目录/文件 | 作用 | 修改边界 |
| --- | --- | --- |
| `*.ioc` | CubeMX 的硬件配置源：时钟、引脚、外设、DMA、中断 | 改动前确认硬件影响；重新生成以它为准 |
| `Core/Inc`、`Core/Src` | CubeMX 生成的 `main.c`、GPIO、CAN、UART、定时器与中断基础代码 | 仅在 `USER CODE BEGIN/END` 区放必要代码，不手改生成区 |
| `Drivers/` | CMSIS、STM32 HAL 等第三方驱动 | 视为依赖库，不直接修改 |
| `startup_*.s`、链接脚本、工具链配置 | 上电启动、内存布局、编译/链接规则 | 通常不修改 |
| `components/`、`middleware/` | 通信管理器、PID、滤波、电机等通用实现 | 可阅读和复用；改动需考虑所有使用者 |
| `instance/`、`device/` | 将通用组件绑定到具体电机、总线或传感器 | 查找硬件实例、协议对象和默认参数 |
| `task/`、`application/` | 定时任务、通信回调、状态机 | 查找控制在哪个周期执行 |
| `robot/`、`modules/` | 上层机器人行为：目标处理、控制串级、安全逻辑 | 控制、坐标、策略修改最常进入这里 |
| `tests/` | 在电脑上运行的协议、限幅、PID 等测试 | 修改算法后优先执行或补充测试 |
| `CMakeLists.txt` / `Makefile` | 组织源文件、工具链和构建产物 | 用来理解工程如何编译，不随意删改源文件列表 |

## 5. 从上电到电机：怎么读下位机数据流

不管工程使用裸机循环还是 RTOS，思路都是：**先初始化，再由固定节拍或任务调度执行控制。** 一个常见的 CubeMX 裸机框架如下：

```mermaid
flowchart TD
    ioc[.ioc] -->|生成| main[main.c]
    main --> hal[HAL_Init]
    hal --> clock[SystemClock_Config]
    clock --> peripheral[MX_*_Init：GPIO、CAN、UART、DMA、TIM]
    peripheral --> appinit[AppInit：创建通信、设备与控制器实例]
    appinit --> schedule[定时器中断 / RTOS 周期任务]
    schedule --> receive[接收通信数据并更新目标]
    receive --> feedback[读取编码器、IMU 等反馈]
    feedback --> control[校验、限幅、滤波、状态机、PID]
    control --> actuator[经 CAN / PWM / 串口输出给执行器]
```

对视觉组来说，需要修改上层算法的，最重要的是确认四件事：

1. 控制函数由哪个定时器/任务调用，周期是多少；
2. 上位机数据在哪个回调进入、何时被写入共享状态；
3. 电机反馈的单位、零点和正方向是什么；
4. 指令在送到电机前经过了哪些限幅、滤波和安全检查。

不要在高频中断或控制任务里加入阻塞通信、文件操作、大量日志或动态内存分配；它们会破坏实时性，表现为控制抖动、丢帧或看似随机的故障。

## 6. 上下位机通信：看语义，不只看字节

通信帧通常长这样：

```mermaid
flowchart LR
    header[帧头 / 消息类型] --> length[长度] --> payload[载荷：若干字段] --> checksum[校验]
```

新人不需要先实现串口驱动，但必须读懂每个字段的**语义、单位、正方向和无效行为**。一份控制接口至少要写清：

| 方向 | 常见字段 | 必须说明的内容 |
| --- | --- | --- |
| 上位机 → 下位机 | 目标 pitch/yaw、目标速度、模式、有效标志 | rad 还是 deg；绝对角还是增量；正方向；超时后如何处理 |
| 下位机 → 上位机 | 当前 pitch/yaw、角速度、设备状态、比赛状态 | 反馈来源；时间戳；是否已滤波；无效值和断线语义 |

最常见的联调错误有三类：

- **单位错**：一个模块用度，另一个模块用弧度；
- **方向错**：图像里向右的误差被解释为云台应向左运动；
- **时效错**：目标已丢失，但控制器继续使用旧包。

排查时依次打印或可视化“上位机输入 → 上位机目标 → 通信字段 → 下位机目标 → 下位机反馈”。每次只验证一个量，例如只验证 yaw 的正方向，再验证 pitch，最后才打开连续跟随。

## 7. CubeMX 重新生成需要注意

`.ioc` 是硬件配置的来源。若要改 UART、CAN、DMA、时钟、引脚或中断优先级，应在 CubeMX 中改 `.ioc` 后重新生成，而不是只改生成的 `.c` 文件。不过其实视觉组这边一边不会和.ioc打交道。重新生成会覆盖大部分 `Core/` 代码，但会保留标记为 `USER CODE` 的区域。

因此建议遵循以下规则：

1. 只改坐标系、目标生成、PID 参数或上层控制时，优先改 `robot/application`、`task` 或项目约定的配置层；
2. 需要改外设配置时，先与电控负责人确认硬件和协议影响；
3. 重新生成后查看 `git diff`，确认用户代码和构建文件都没有丢失；
4. 不修改 `Drivers/`，不把“临时改一下生成的 UART/CAN 文件”当作长期方案。

## 8. 推荐的阅读顺序

面对一个陌生项目，可按这条路线建立全局认识：

```mermaid
flowchart LR
    start[启动 / 参数文件] --> messages[上位机消息定义与数据流]
    messages --> protocol[通信协议字段]
    protocol --> init[下位机 .ioc 与 main.c 初始化]
    init --> task[下位机任务入口和控制周期]
    task --> algorithm[上层控制、坐标变换、PID 与安全状态]
```

这条路线的目的不是让你立刻写底层，而是让你能安全地完成“读懂现成项目 → 修改上层算法或参数 → 编译烧录 → 用反馈验证”的闭环。凡是涉及硬件接线、外设初始化、DMA/中断配置或协议变更的修改，都应和电控负责人一起完成。
